# راهنمای راه‌اندازی Paperclip + Herdr برای تقسیم کار بین چند ایجنت

**Paperclip** فهرست اعضای شرکت، کارها، مسئول هر کار و وضعیت بازبینی را نگه می‌دارد. **Herdr** محیطی است که برنامهٔ ایجنت در آن اجرا می‌شود. نصب Freebuff یا اجرای `agy` به‌تنهایی رکوردی در فهرست **Agents** شرکت نمی‌سازد.

## مسیر کوتاه: از فهرست خالی تا اولین واگذاری

1. در ویندوز `setup-dashboard.cmd` را از ریشهٔ مخزن اجرا کنید. اگر شرکت ندارید، یک‌بار در Paperclip (`http://localhost:3100`) بسازید. نام همان شرکت باید بالای داشبورد دوزبانه (`http://localhost:8000`) باشد.
2. در **تیم ایجنت‌ها** یک عضو ثبت کنید. برای **Freebuff**، «دستی» کافی است. برای **Antigravity**، `agy` را در پوشهٔ پروژه داخل Herdr باز کنید، منتظر آماده‌شدنش بمانید و اول نشست سرور و سپس ایجنت همان نشست را از فهرست انتخاب کنید. «ایجنت دیگر» نیز همین دو روش را دارد. عضوی که از قبل در Paperclip ساخته‌اید برای تقسیم کار به ثبت دوباره نیاز ندارد. اگر استخدام منتظر تأیید است، در **Paperclip → Approvals** آن را بررسی کنید.
3. در **میز تقسیم کار** عنوان کار اصلی را بنویسید یا یک تیکت موجود را انتخاب کنید. برای هر زیرکار یک خروجی و یک مسئول بگذارید؛ مثلاً برای «جست‌وجوی مشتریان»، ساخت فیلتر با Antigravity و آزمایش نتایج خالی با Freebuff. **ثبت طرح در Paperclip** تیکت‌های مرتبط را در `backlog` می‌سازد؛ هنوز چیزی به ترمینال نمی‌فرستد.
4. در **کارهای شرکت** فقط زیرکار آماده را شروع کنید: برای عضو متصل «ارسال به صف اجرا»؛ برای عضو دستی «شروع دستی» و کپی «برگهٔ کار» **در خودِ برنامهٔ ایجنت، نه در شل**. نتیجه را از «بازبینی در Paperclip» بررسی کنید.

از بالای میز با **فارسی / English** زبان و جهت صفحه را عوض کنید. انتخاب زبان در همین مرورگر می‌ماند؛ متن تیکت‌ها، نام اعضا و پیش‌نویس شما ترجمه یا جایگزین نمی‌شوند.

برای این مسیر به Hermes، Bash، `jq`، MCP، ساخت کلید برای هر ایجنت یا نوشتن JSON نیاز نیست. [راهنمای میز کار و رفع اشکال](../dashboard/README.md) · [شواهد آزمون و محدودیت‌ها](../PROJECT_STATUS.md). برای اجرای فقط Paperclip، از ریشه `npm ci` و سپس `npm start` را بزنید. راه‌اندازی اولیه در بخش ۲ توضیح داده شده است.

## ۲. نصب Paperclip

این مخزن **سرور Paperclip را از بستهٔ رسمی `paperclipai`** نصب می‌کند؛ `paperclip` در npm پروژهٔ دیگری است. خودِ `npm install` سرور را اجرا نمی‌کند. از پوشه‌ای که `package.json` و `setup-dashboard.cmd` در آن هستند شروع کنید. Node سری ۲۴ را به‌روز کنید: حداقل خودِ CLI نسخهٔ 24.11 است، ولی وابستگی‌های قفل‌شدهٔ این پروژه روی سری ۲۴ به **24.15.0 یا جدیدتر** نیاز دارند. برای رعایت سیاست اسکریپت‌های نصب، **npm 11.16.0 یا بالاتر** لازم است. اگر npm قدیمی است، بعد از به‌روزرسانی Node با `npm install -g npm@11` آن را به‌روز و ترمینال را دوباره باز کنید.

</div>

```bash
npm ci       # نصب اولیه یا پس از تغییر package-lock.json
npm start    # این ترمینال را باز نگه دارید؛ توقف با Ctrl+C
```

<div dir="rtl">

- `npm start` بار اول تنظیمات و PostgreSQL داخلی را می‌سازد و در دفعات بعد تنظیمات موجود را نگه می‌دارد. نصب و مهاجرت اولیه ممکن است چند دقیقه طول بکشد و نصب به چند گیگابایت فضای خالی نیاز دارد. سرویس پس‌زمینه نصب نمی‌شود.
- در این ترکیب به Copilot احتیاجی نیست. مرحلهٔ پرمصرف آماده‌سازی باینری **اختیاری Copilot** از نصب اصلی جدا شده است؛ PostgreSQL و بقیهٔ اجزای لازم همچنان نصب می‌شوند. فقط در صورت نیاز به آن آداپتور روی سکوی پشتیبانی‌شده، بعد از پایان نصب `npm run setup:copilot` را اجرا کنید.
- رابط **Paperclip** معمولاً روی `http://localhost:3100` است. آدرس چاپ‌شده در ترمینال ملاک است. `http://localhost:3100/api/health` باید JSON با `status: "ok"` برگرداند. پاسخ `[]` از `/api/companies` یعنی سرور آماده است ولی هنوز شرکتی نساخته‌اید.
- برای دیدن ایجنت‌ها و تیکت‌ها، در رابط Paperclip شرکت خودتان را بسازید. اگر تنها یک شرکت باشد داشبورد آن را خودکار پیدا می‌کند. اگر چند شرکت دارید، `PAPERCLIP_COMPANY_ID` را در `dashboard/.env` تعیین کنید.
- **داشبورد دوزبانه** برنامهٔ جداگانه‌ای است. در ترمینال دوم `python dashboard/app.py` (در لینوکس/مک: `python3 dashboard/app.py`) را اجرا کنید و `http://localhost:8000` را باز کنید. [تنظیمات و آزمون اتصال داشبورد](../dashboard/README.md).
- **ویندوز:** به‌جای دو ترمینال می‌توانید `.\setup-dashboard.cmd` را اجرا کنید. راه‌انداز جدیدترین مفسر سازگار Python 3 را پیدا می‌کند و فایل اجرایی واقعی آن را به کار می‌گیرد؛ PyManager لازم نیست. برای انتخاب نسخه، مثلاً `.\setup-dashboard.cmd -PythonVersion 3.14` را بزنید. اگر Paperclip آماده باشد دوباره آن را اجرا نمی‌کند؛ فقط برای آدرس محلی پیش‌فرض و در نبود سرویس از بستهٔ محلی پروژه استفاده می‌کند (در صورت نیاز ابتدا `npm.cmd ci`). [انتخاب مسیر پایتون و عیب‌یابی مهلت اتصال](../dashboard/README.md).
- اگر قبلاً **بستهٔ درست** را سراسری نصب کرده‌اید، می‌توانید به‌جای مسیر پروژه در یک ترمینال `paperclipai onboard --yes` (بار اول) یا `paperclipai run` (با تنظیمات موجود) را اجرا کنید. هم‌زمان `npm start` دیگری برای همان نمونه نزنید. نصب سراسری تابع فایل قفل و اصلاحیه‌های امنیتی این مخزن نیست؛ برای نصب جدید مسیر `npm ci` و `npm start` را ترجیح دهید.

**اگر با npm نصب شد ولی جواب نگرفتید:**

| بررسی | اقدام |
|---|---|
| `ENOENT ... package.json` | ترمینال را در ریشهٔ این مخزن باز کنید. |
| `EBADENGINE`، `node` پیدا نشد یا PowerShell اجرای `npm.ps1` را مسدود کرد | `node -v`، `npm.cmd -v` و در ویندوز `where.exe node` را ببینید. پس از نصب Node سازگار ترمینال جدید باز کنید؛ از `npm.cmd ci` و `npm.cmd start` استفاده کنید. |
| `paperclipai` پیدا نشد یا بستهٔ بومی PostgreSQL نصب نشده | `npm ci` باید بدون خطا تمام شود. وابستگی‌های اختیاری یا اسکریپت‌های نصب را حذف نکنید. `npm ls paperclipai`، فضای دیسک، معماری سیستم (بستهٔ PostgreSQL ویندوز: x64) و **اولین خطای npm** را بررسی کنید. |
| `E404` یا خطای دریافت بسته | با `npm config get registry` مطمئن شوید رجیستری شما بستهٔ رسمی را در دسترس دارد. |
| `Refusing to reuse PostgreSQL` | [بررسی فقط‌خواندنی نمونهٔ قبلی](#postgres-reuse)؛ قفل را پاک نکنید. |
| `/api/health` پاسخ نمی‌دهد | خروجی ترمینال `npm start` و `npm run doctor`، مسیر داده و پورتی که واقعاً چاپ شده را بررسی کنید. دادهٔ نمونهٔ قبلی را پاک نکنید. |
| سرور سالم است ولی داشبورد داده ندارد | `python dashboard/test_connectivity.py` را اجرا کنید. آدرس پایه بدون `/api` است. شناسهٔ ثابت یا کلید نمایشی مانده از نصب قبلی را از `dashboard/.env` بردارید؛ برای نمونهٔ احراز هویت‌شده کلید مجاز تنظیم کنید. بعد از ویرایش، **داشبورد** را دوباره اجرا کنید. |

**مسیر دادهٔ دلخواه:** در هر بار اجرا همان مسیر و همان کاربر سیستم‌عامل را استفاده کنید. داده‌های Paperclip در `node_modules` نیستند.

</div>

```bash
npm start -- --data-dir "D:/AI-Workspace/paperclip-data"
# تشخیص همان نمونه:
npm run doctor -- --data-dir "D:/AI-Workspace/paperclip-data"
```

## ۶. راه‌اندازی ایجنت‌ها در Herdr

هر ایجنت مجری در یک پنجرهٔ Herdr و در **worktree جدا** اجرا می‌شود تا فایل‌های هم را خراب نکنند. پروژه باید یک ریپوی Git باشد.

### Antigravity

</div>

```bash
# Git Bash / مک / لینوکس
created=$(herdr worktree create --cwd /path/to/project --branch feat-agy --no-focus)
echo "$created" | jq .           # ساختار خروجی را ببینید و شناسهٔ پنجره را بردارید
pane=$(echo "$created" | jq -r '.result.root_pane.pane_id')

herdr agent start agy-worker --kind agy --pane "$pane"
```

```powershell
# PowerShell
$created = herdr worktree create --cwd D:\My-Code-Project --branch feat-agy --no-focus | ConvertFrom-Json
$pane = $created.result.root_pane.pane_id
herdr agent start agy-worker --kind agy --pane $pane
```

<div dir="rtl">

- `agy-worker` نام ایجنت است؛ بعد از انتخاب نشست سرور در فهرست دوم ظاهر می‌شود. از همان کاربر و همان نشست Herdr استفاده کنید. برای مسیر ساده، باز کردن `agy` در یک پنجرهٔ پروژه و انتخاب آن از فهرست کافی است.
- **تأییدنشده:** مسیر `.result.root_pane.pane_id` برای دستور `workspace create` مستند است؛ برای `worktree create` فرض کرده‌ام همان است. اگر خالی بود، خروجی JSON را نگاه کنید.

### Freebuff

</div>

```bash
created=$(herdr worktree create --cwd /path/to/project --branch feat-freebuff --no-focus)
fb_pane=$(echo "$created" | jq -r '.result.root_pane.pane_id')
herdr pane run "$fb_pane" "freebuff"
echo "$fb_pane"     # مثلاً w2:p1 — یادداشت کنید
```

<div dir="rtl">

در مسیر دستی، کافی است خودتان Freebuff را در پنجرهٔ پروژه اجرا کنید؛ تشخیص آن توسط Herdr شرط نیست. برای چند مجری هم‌زمان، از نشست‌ها و worktreeهای جدا استفاده کنید. میز کار خودش worktree نمی‌سازد و branchها را ادغام نمی‌کند.

## ۷. اتصال Antigravity

در «تیم ایجنت‌ها» پیش‌تنظیم **Antigravity** و حالت **متصل** را انتخاب کنید. «یافتن نشست‌ها» ابتدا `herdr session list --json` را می‌خواند. نشست سرور را انتخاب کنید؛ فهرست دوم از `agent list` همان نشست می‌آید. ایجنت شناسایی‌شده را انتخاب و «ثبت در شرکت» را بزنید. اسم نمایشی در Paperclip لازم نیست همان نام نشست باشد. اگر فهرست خالی است، ابتدا ورود و آمادگی `agy` در Herdr را بررسی کنید؛ یا همین امروز با روش دستی کار کنید.

عضو جدید از آداپتور عمومی **process** با worker پایتون همین مخزن استفاده می‌کند؛ نیازی به آداپتور اختصاصی Antigravity نیست. مسیر مفسر و worker هنگام ثبت ذخیره می‌شود، پس مخزن باید برای Paperclip روی همین رایانه قابل دسترس بماند. هر ایجنت ترمینالی را فقط به یک عضو وصل کنید. برای ایجنت بی‌نام، شمارهٔ پنجره به **شناسهٔ همان ترمینال** مقید است؛ استفادهٔ مجدد از شمارهٔ پنجره به‌تنهایی اتصال قبلی را معتبر نمی‌کند. هنگام ثبت جدید، نام نشست سرور و فایل اجرایی Herdr هم در تنظیمات worker ثبت می‌شوند. اتصال‌های قدیمی خودکار جابه‌جا نمی‌شوند.

اگر از قبل ایجنتی با `bridge.sh` دارید، آداپتورش تغییر نمی‌کند؛ توضیح پل قدیمی در بخش ۱۰ آمده است. برای همان نشست هم‌زمان دو worker راه نیندازید.

<a id="freebuff"></a>

## ۸. اتصال Freebuff

«تیم ایجنت‌ها → Freebuff → دستی → ثبت در شرکت» یک **عضو واقعی** برای واگذاری می‌سازد، نه یک برنامهٔ در حال اجرا. این حالت به MCP، کلید مخصوص ایجنت یا شناسایی Freebuff توسط Herdr نیاز ندارد. برگهٔ زیرکار را کپی کنید، آن را در خودِ Freebuff اجرا کنید، بعد از بررسی نتیجه «آمادهٔ بازبینی» را بزنید. در این روش هیچ ورودی خودکاری به پنجرهٔ ناشناخته ارسال نمی‌شود. برای ابزارهای دیگر هم می‌توانید نام و روش تحویل را انتخاب کنید. تنها اگر `herdr agent list` واقعاً ابزار را تشخیص می‌دهد، روش متصل را به کار ببرید.

<a id="daily"></a>

## ۹. گردش کار روزانه

- **برنامه‌ریزی:** تیکت اصلی + ۱ تا ۲۰ زیرکار با مسئول مشخص. الگوی سه‌مرحله‌ای فقط نقطهٔ شروعِ قابل‌ویرایش است؛ هوش مصنوعی مسئول‌ها را حدس نمی‌زند.
- **شروع:** روی «ارسال به صف اجرا» بزنید تا تیکت از `backlog` به `todo` برود؛ این تغییر خودش می‌تواند Paperclip را به اجرا وادارد، بیدارباش دوم لازم نیست. در حالت دستی شروع به `in_progress` می‌رود. ترتیب ردیف‌ها وابستگی اجرایی ایجاد نمی‌کند؛ مرحلهٔ وابسته را وقتی آماده شد آزاد کنید.
- **تحویل:** worker متصل فقط برای تیکت واگذارشده، با مالکیت اجرای فعلی و نشست آماده کار می‌کند. بازگشت ایجنت به حالت بیکار **معادل درست‌بودن خروجی نیست**؛ worker یک درخواست بازبینی انسانی روی همان تیکت می‌سازد. مسئول نهایی در Paperclip تصمیم می‌گیرد کار بسته یا اصلاح شود.
- **خطا:** اگر ارسال، انتظار یا ثبت بازبینی نامشخص ماند، قبل از بیدارباش یا واگذاری دوباره، نشست و صفحهٔ اجرای همان تیکت را بررسی کنید. «تلاش مجدد همین طرح» فقط مربوط به **ساخت تیکت‌ها** است، نه ارسال دوبارهٔ کار به ترمینال.

## ۱۰. تنظیمات `bridge.sh`

این بخش برای نگهداری آداپتور Bash **قدیمی** است؛ اعضایی که میز کار ثبت می‌کند از آن استفاده نمی‌کنند. پل قدیمی خروجی ترمینال را در کامنت کپی می‌کند و برای تغییر وضعیت به `in_review` فقط یک PATCH می‌فرستد؛ در نسخهٔ قفل‌شدهٔ Paperclip بدون مسیر معتبر بازبینی ممکن است `422` بگیرد. در این صورت تیکت و خروجی را بررسی کنید، کار انجام‌شده را دوباره اجرا نکنید.

این متغیرها فقط در `adapterConfig.env` آداپتور قدیمی تنظیم می‌شوند:

| متغیر | معنی | پیش‌فرض |
|---|---|---|
| `HERDR_TARGET` | نام ایجنت یا شناسهٔ پنجره در Herdr (اجباری) | — |
| `HERDR_MODE` | `agent` برای ایجنت‌های شناخته‌شدهٔ Herdr؛ `pane` برای بقیه (مثل Freebuff) | `agent` |
| `WAIT_MS` | حداکثر زمان یک تیکت (میلی‌ثانیه) | `1800000` (۳۰ دقیقه) |
| `QUIET_SEC` | در حالت `pane`: چند ثانیه صفحهٔ بدون تغییر یعنی «تمام شد» | `45` |
| `DONE_STATUS` | وضعیتی که بعد از پایان روی تیکت گذاشته می‌شود | `in_review` |

**اسکریپت چه می‌کند**

1. اولین تیکت `in_progress` یا `todo` واگذارشده به ایجنت را می‌خواند.
2. آن را برمی‌دارد (checkout). فقط در تداخل مالکیت (`HTTP 409`) کنار می‌رود؛ خطای مجوز یا اتصال را به‌عنوان موفقیت گزارش نمی‌کند.
3. عنوان و شرح تیکت را در پنجرهٔ ایجنت تایپ می‌کند.
4. صبر می‌کند تا کار تمام شود:
   - حالت `agent`: از تشخیص وضعیت خود Herdr استفاده می‌کند.
   - حالت `pane`: منتظر یک نشانهٔ پایان (`PAPERCLIP_DONE_...`) در خروجی می‌ماند؛ اگر نیامد، سکوت صفحه ملاک است.
5. ۱۲۰ خط آخر خروجی را روی تیکت کامنت می‌گذارد و وضعیت را تغییر می‌دهد.
6. اگر ارسال پرامپت یا خواندن خروجی ناموفق باشد، ایجنت گیر کند یا زمان تمام شود، تیکت را باز می‌گذارد.

**خودکار کردن Freebuff (آزمایشی):** می‌توانید به‌جای آداپتور بی‌اثر، همان `bridge.sh` را با `HERDR_TARGET=<شناسهٔ پنجره>` و `HERDR_MODE=pane` بدهید. این حالت شکننده است و ممکن است با شرایط استفادهٔ Freebuff (سرویس رایگان مبتنی بر تبلیغ) سازگار نباشد؛ خودتان بررسی کنید.

<a id="limitations"></a>

## ۱۱. محدودیت‌ها

- **امنیت:** این راه‌اندازی برای استفادهٔ محلی است. گزارش وابستگی‌های باقی‌مانده و محدودیت انتشار در [SECURITY.md](../SECURITY.md) آمده است.

- **پرسش‌های تأیید:** اگر ایجنت وسط کار اجازه بخواهد، اسکریپت جواب نمی‌دهد و تیکت باز می‌ماند.
- **Antigravity:** طبق مستندات Herdr، به‌محض برگشتن به خط فرمان «بیکار» حساب می‌شود، حتی اگر کار پس‌زمینه‌اش ادامه داشته باشد.
- **گزارش و هزینه:** برای ایجنت‌های `process`، Paperclip فقط کامنت‌های ثبت‌شده را می‌بیند؛ گزارش زندهٔ اجرا و آمار هزینه ندارد.
- **یک تیکت در هر بیدارباش:** اسکریپت در هر اجرا فقط یک تیکت را انجام می‌دهد.
- **دامنهٔ آزمایش:** استخدام، واگذاری، اجرای worker و درخواست بازبینی با Paperclip واقعی و CLI ساختگی Herdr آزموده شدند؛ این آزمون جای اجرای برنامهٔ واقعی روی ویندوز شما نیست.
- **Freebuff:** پیش‌فرض میز کار تحویل دستی است. سکوت صفحه را نشانهٔ موفقیت کار نمی‌گیرد.

## ۱۲. رفع اشکال

<a id="postgres-reuse"></a>

### خطای «Refusing to reuse PostgreSQL» در ویندوز

این خطا را **خود Paperclip پیش از شروع داشبورد** می‌دهد. Paperclip در `postmaster.pid` شناسهٔ پردازشی زنده دیده و از PostgreSQL پرسیده «پوشهٔ داده‌ات کجاست؟». در نسخهٔ این مخزن، **هم جواب نگرفتن از SQL و هم متفاوت بودن مسیرِ جواب** همین پیام را می‌دهند. سبز بودن بررسی پوشه در `doctor` به معنی موفقیت اتصال نیست؛ `exit code 1` راه‌انداز هم نتیجهٔ خطاست، نه علت آن.

**اگر برد قبلی باز است،** آدرس همان سرور را که در ترمینالش چاپ شده بررسی کنید. پورت API با پورت دیتابیس یکی نیست:

</div>

```powershell
$board = 'http://127.0.0.1:3100' # use the actual base URL of your original board
(Invoke-RestMethod "$board/api/health" -TimeoutSec 5).status
```

<div dir="rtl">

فقط اگر جواب `ok` است **و در همان برد شرکت و تیکت‌های قبلی خودتان را می‌بینید**، میز را به آن وصل کنید. `-ExistingOnly` حتی اگر اتصال قطع شود Paperclip دیگری راه نمی‌اندازد:

</div>

```powershell
.\setup-dashboard.cmd -ExistingOnly -PaperclipUrl "$board"
```

<div dir="rtl">

**اگر برد در دسترس نیست،** از ریشهٔ مخزن و با همان کاربر و محیط ویندوز، مسیر کامل بعد از `Config:` در خروجی اجرای ناموفق را در پاسخ به فرمان اول بچسبانید (بدون گیومه):

</div>

```powershell
$cfg = Read-Host 'Config path'
.\setup-dashboard.cmd -DiagnosePostgres -ConfigPath "$cfg"
```

<div dir="rtl">

اگر خط `Config:` را ندارید، `.\setup-dashboard.cmd -DiagnosePostgres` را بدون مسیر بزنید. ابزار به‌ترتیب `PAPERCLIP_CONFIG`، نزدیک‌ترین `.paperclip/config.json` یا تنظیمات home/instance جاری را بررسی و مسیر انتخابی را **برای مقایسه در رایانهٔ خودتان** چاپ می‌کند. `-ConfigPath` فقط برای تشخیص است. `--data-dir` در Paperclip به **خانهٔ Paperclip** اشاره دارد، نه پوشهٔ `db`.

این فرمان چیزی نصب نمی‌کند، سرویس را راه نمی‌اندازد یا متوقف نمی‌کند، `doctor` را اجرا نمی‌کند و قفل، داده یا `.env` را تغییر نمی‌دهد. معیار آن پیکربندی صریح دیتابیس داخلی است؛ متغیرهای فایل `.env` را بارگذاری نمی‌کند. فقط اگر PID، مالکِ پورت در ویندوز و مسیر داخل قفل تأیید شوند، روی `127.0.0.1` **با پورت واقعیِ ثبت‌شده در قفل** یک پرس‌وجوی فقط‌خواندنی انجام می‌دهد.

| نتیجهٔ `DB-CHECK` | برداشت و اقدام |
|---|---|
| `server-dir-matches` | **الان** پاسخ SQL با مسیر تنظیمات می‌خواند. آدرس API و شرکت برد قبلی را بررسی کنید؛ این نتیجه مجوز اجرای سرور دوم نیست. |
| `same-dir-different-spelling` یا `dir-identity-unverified` | نوشتار مسیرها پس از نرمال‌سازی متفاوت است؛ در اولی شناسهٔ پوشه در فایل‌سیستم یکی است و در دومی هویت مشخص نیست. مسیر و درایو اجرای قبلی (از جمله حروف بزرگ/کوچک یا junction) را بررسی کنید. پوشه را تغییر نام ندهید و محافظ Paperclip را دور نزنید. |
| `server-dir-differs`، `pid-file-dir-differs`، `listener-owner-differs` یا `pid-not-postgres` | پوشه، اطلاعات قفل یا پردازش با انتظار نمی‌خواند؛ حتی ممکن است ویندوز PID را به برنامهٔ دیگری داده باشد. چیزی را نبندید. اول نمونه، مالک و فرمان اجرای اصلی را شناسایی کنید. |
| `sql-auth-failed` | ورود یا اجازهٔ خواندن تنظیم رد شده است. گزارش محلی PostgreSQL همان نمونه را بررسی کنید؛ رمز یا قواعد ورود را برای رد شدن از بررسی تغییر ندهید. |
| `sql-not-ready`، `sql-timeout` یا `sql-unavailable` | پاسخ SQL به دست نیامده؛ دیتابیسِ متفاوت ثابت نشده است. اگر سرویس اصلی در حال بالا آمدن است صبر کنید و **بررسی** را تکرار کنید، نه راه‌اندازی را. |
| تنظیمات/قفل خوانده نشد، PID یا پورت پیدا نشد، `*-unverified` یا `probe-unavailable` | مالکیت تأیید نشده. مسیر `Config:`، کاربر و محیط اجرای اصلی را مقایسه کنید. بخش SQL به `node.exe` و بستهٔ `postgres` از نصب قبلی همین پروژه نیاز دارد. |

`postmaster.pid` را پاک نکنید، PID را با `taskkill` نبندید و برای رفع این خطا home جدید یا دیتابیس دیگری انتخاب نکنید. اگر راه‌اندازی مجدد لازم شد، **فقط نمونهٔ اصلی که مالک آن را شناخته‌اید** از ترمینال یا مدیر سرویس خودش به‌طور عادی متوقف شود. قبل از هر تعمیر داده، نمونه و پشتیبان آن را تأیید کنید. برای پیگیری فقط **خط `DB-CHECK: …`، نتیجهٔ سلامت (`ok` یا نه) و اینکه مسیر تنظیمات همان قبلی بود یا نه** کافی است؛ مسیر شخصی، فایل تنظیمات، `.env`، رمز و لاگ کامل را نفرستید.

<a id="desk-diagnostics"></a>

### نشست سرور با پنجره و ایجنت یکی نیست

در **PowerShell تازه** با همان کاربر و سطح دسترسیِ داشبورد، بدون Administrator در حالت عادی:

</div>

```powershell
Get-Command herdr.exe -ErrorAction SilentlyContinue
herdr --version
(herdr session list --json | ConvertFrom-Json).sessions | Select-Object name,running
```

<div dir="rtl">

1. **دستور پیدا نشد؟** [نسخهٔ رسمی ویندوز](https://github.com/herdrdev/herdr/releases) را نصب کنید و ترمینال و داشبورد را دوباره باز کنید. اگر CLI در شل شما کار می‌کند ولی میز آن را نمی‌بیند، در `dashboard/.env` مقدار `HERDR_DESK_EXE` را **مسیر کامل فایل واقعی `herdr.exe`** بگذارید. مسیر پایدار نصب معمولاً `%LOCALAPPDATA%\Programs\Herdr\bin\herdr.exe` است؛ در فایل `.env` مسیر کامل را بنویسید، نه `%LOCALAPPDATA%`. فایل exe را از بقیهٔ بسته جدا نکنید.
2. **هیچ `running=True` نیست؟** در ترمینال دیگری در پوشهٔ پروژه، `herdr` را باز کنید (برای نشست نام‌دار مثلاً `herdr --session studio`). **داخل یکی از پنجره‌های آن**، `agy` را اجرا کنید و ورودش را کامل کنید. داخل Herdr دوباره `herdr` اجرا نکنید.
3. **نشست روشن است ولی فهرست ایجنت خالی است؟** در ترمینال **بیرونی** دستورهای زیر را اجرا کنید. به‌جای `studio` نام واقعی نشست را بگذارید؛ نام نشست پیش‌فرض `default` است.

</div>

```powershell
herdr --session studio pane list
herdr --session studio agent list
```

<div dir="rtl">

`pane list` فقط وجود پنجره‌ها را نشان می‌دهد. در `agent list` (بدون `--json`) باید در `result.agents` یک ایجنت دیده شود. شل خالی، پنجرهٔ مستقل برنامه یا ثبت اسم در Paperclip ایجنتِ شناسایی‌شده نیست. حالا در میز **یافتن نشست‌ها ← نشست سرور ← ایجنت همان نشست** را انتخاب کنید. اگر ابزار شناسایی نمی‌شود، برای Freebuff یا «ایجنت دیگر» **تحویل دستی** را انتخاب کنید؛ لازم نیست کاری به شل فرستاده شود.

میز نشست‌های محلی پیش‌فرض و نام‌دار را می‌بیند، نه سوکت سفارشی یا سرور راه دور را. هر سه برنامه باید از یک حساب، محیط (ویندوز یا WSL)، سطح دسترسی و محل تنظیمات Herdr استفاده کنند. اگر خطای نسخهٔ پروتکل دارید، `herdr --version` و `herdr --session studio status` را مقایسه کنید؛ **قبل از توقف سرور کار باز را حفظ کنید** چون پنجره‌هایش بسته می‌شوند.

<a id="verification"></a>

### Hermes-CEO: «Agent verification failed» به معنی اجرای ناموفق تیکت نیست

از کارت **همان عضو** روی «تنظیمات و آزمون اجرا» بزنید. در Paperclip مسیر **Harness / Runtime → Run test → Test details** را باز کنید. **اولین خطا** و اگر خطایی نیست **اولین هشدار** را بخوانید. نام «CEO» نوع آداپتور را مشخص نمی‌کند. آزمون اتصال مدیریت‌شده ممکن است با مدل تماس بگیرد؛ میز آن را خودکار اجرا نمی‌کند.

| نتیجهٔ بررسی | اقدام |
|---|---|
| `hermes_local` و خطای CLI یا نسخه | در محیطی که **سرور Paperclip** از آن شروع می‌شود `Get-Command hermes -All` و `hermes --version` را بررسی کنید. آداپتور CLI را مستقیماً اجرا می‌کند؛ alias پاورشل، تنها یک فایل `.cmd`، میان‌بر دسکتاپ یا نصب در WSL دیگر کافی نیست. اگر فرمان سفارشی دارید، مسیر فایل اجرایی واقعی CLI را بدهید. |
| `hermes_python_missing` یا `hermes_python_old` | آزمون محلیِ بدون اتصال مدیریت‌شده دقیقاً `python3 --version` را می‌زند و ۳.۱۰ به بالا می‌خواهد، نه `py` یا `python.exe` انتخاب‌شدهٔ داشبورد. `python3` واقعی باید در PATH خود Paperclip قابل اجرا باشد. پس از تغییر PATH، وقتی کار بازی در خطر نیست **همان نمونهٔ Paperclip** را از یک ترمینال تازه راه‌اندازی کنید؛ سرور دوم نسازید. |
| `hermes_no_api_keys`، ناسازگاری provider/model یا `hermes_hello_probe_failed` | در حالت محلی تنظیمات `hermes setup` را برای مدل موردنظر بررسی کنید. برای اتصال مدیریت‌شده، اتصال انتخابی **همان عضو**، مدل و endpoint را بررسی کنید؛ ورود موفق در شلی دیگر مدرک نیست. در نسخهٔ قفل‌شدهٔ Paperclip حتی نتیجهٔ کلی `warn` بدون آزمون تأییدکنندهٔ موفق می‌تواند مانع آماده‌شدن عضو شود. |
| `hermes_gateway` و خطای نشانی، مجوز یا health | نشانی پایهٔ **سرور API هرمس**، اعتبارنامهٔ متناظر و دسترسی از محیط Paperclip را بررسی کنید؛ برای سرور غیرمحلی از HTTPS استفاده کنید. این اعتبارنامه کلید برد Paperclip نیست. نصب Herdr تغییری در این بررسی نمی‌دهد. |

پس از اصلاح، تغییرات را ذخیره کنید و دوباره **Run test** را بزنید. اگر موفق شد و عضو هنوز در مرحلهٔ تأیید ماند، **Retry now** را بزنید. این دکمه تأیید را تکرار می‌کند، نه اجرای کار را. میز تا `ready` شدن عضو اجازهٔ واگذاری یا بیدارباش نمی‌دهد.

### در عنوان `CYR-2` چه بنویسم؟

`CYR-2` **شناسهٔ تیکت** است، نه عنوان. اگر شرح کار دربارهٔ ساخت همین داشبورد است، این عنوان را کپی کنید:

**ایجاد داشبورد یکپارچه Paperclip+Herdr**

1. در **Paperclip → Issues** همان `CYR-2` را باز کنید (یا از میز، «اصلاح عنوان در Paperclip» را بزنید). اگر عنوان آنجا درست است، **تغییرش ندهید**.
2. اگر آنجا هم `????? ??????? ??????? Paperclip+Herdr` ذخیره شده، روی خودِ عنوان کلیک کنید، متن پیشنهادی یا عنوانی مطابق شرح واقعی کار را وارد کنید و **Enter** بزنید. شناسه را به عنوان اضافه نکنید؛ تیکت دیگری نسازید.
3. میز را تازه‌سازی کنید؛ همان شناسه باید با عنوان خوانا دیده شود. پیشنهاد میز بازیابی متن اصلی نیست: از روی تعداد `?` نمی‌شود کلمات از دست رفته را فهمید. میز دادهٔ شرکت را خودکار بازنویسی نمی‌کند.

الگوی سه‌مرحله‌ای عنوان ناخوانا را به زیرکارها کپی نمی‌کند. هنگام ساخت طرح، عنوان‌های جدیدِ دارای کلمهٔ جداگانه از سه یا چند `?` یا نویسهٔ جایگزین `�` **قبل از ساخت هر تیکت** برای اصلاح برگردانده می‌شوند؛ سؤال معمولی انگلیسی یا فارسی (`Why?`، `چرا؟`) معتبر است. برای کار اصلی موجود همچنان می‌توانید زیرکارها را با عنوان‌های خوانای خودتان بنویسید. برای بررسی فقط‌خواندنی تیکت باز در میز محلی:

</div>

```powershell
(Invoke-RestMethod http://127.0.0.1:8000/api/tickets).tickets | Where-Object identifier -eq 'CYR-2' | Select-Object identifier,titleWarning
```

`literal_question_marks` یعنی علامت سؤال‌های واقعی در متن API؛ `replacement_character` یعنی نویسهٔ جایگزین `�`. این نتیجه **علت خرابی** را مشخص نمی‌کند. اگر ردیفی نیست، نام شرکت و باز بودن تیکت را بررسی کنید. برای ادامهٔ عیب‌یابی فقط نتیجهٔ همین بررسی، پیام/کد اولین بررسی ناموفق Hermes، نسخهٔ Herdr و وجود یا نبود نشست و ایجنت لازم است؛ کلید، فایل `.env`، پاسخ کامل تست یا متن ترمینال را ارسال نکنید.

### پل Bash قدیمی

| نشانه | علت محتمل | راه‌حل |
|---|---|---|
| `'bash\r': No such file or directory` | پایان خط ویندوزی در اسکریپت | `sed -i 's/\r$//' bridge.sh` |
| `command not found` در خط‌های اسکریپت | متن از چت کپی شده و کاراکتر مخفی دارد | فایل را دانلود کنید |
| `jq: command not found` یا `herdr: command not found` | ابزار در مسیر Git Bash نیست | Git Bash جدید باز کنید؛ در صورت نیاز مسیر را در `adapterConfig.env.PATH` بدهید |
| `checkout refused, skipping` | ایجنت دیگری تیکت را برداشته | اجرای مسئول فعلی را بررسی کنید؛ کار را دوباره نفرستید |
| `no assigned work` | تیکتی با وضعیت `todo` یا `in_progress` به این ایجنت واگذار نشده | واگذاری و وضعیت تیکت را بررسی کنید |
| اسکریپت تا ۳۰ دقیقه منتظر می‌ماند | ایجنت نشانهٔ پایان را چاپ نکرده و صفحه متحرک است | `WAIT_MS` را کم کنید یا خروجی پنجره را ببینید |
| `state=blocked` و تیکت باز مانده | ایجنت منتظر تأیید است | در Herdr به پنجرهٔ ایجنت بروید و جواب دهید |
| Herdr ایجنت را پیدا نمی‌کند | Paperclip و Herdr با دو کاربر متفاوت اجرا شده‌اند | هر دو را با یک کاربر اجرا کنید |
| خطای `curl` با کد 4xx در گام اول | شکل پاسخ یا مسیر API با مستندات فرق دارد | متن خطا را نگه دارید تا اسکریپت اصلاح شود |
